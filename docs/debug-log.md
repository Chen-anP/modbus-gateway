## 1. 传感器能收到请求，但中控收不到任何回复

### 环境

```
中控 CH1（USART2）── Hub 1A / 1B ─┐
中控 CH2（UART4） ── Hub 2A / 2B ─┤ Hub（USB 供电）── 四线（A、B、VIN、GND）── 传感器板
                                   │
                                   └ 中控和传感器之间：Modbus RTU，115200 8N1
```

- 中控：本项目固件，测试任务 `bus_probe` 每秒向每一路发一次"读输入寄存器"请求，超时 100 ms
- 传感器：STM32F030（Cortex-M0），运行课程提供的传感器程序（libmodbus 从机）。同一份代码可以编译成 Bootloader 版（链接在 `0x08000000`）或 App 版（链接在 `0x08020000`）

### 现象

中控每一路都打印：

```
D ch2: tx 8 bytes: 03 04 00 00 00 02 70 29
W ch2: no byte received in 100 ms
W ch2: dev 3: timeout
I probe: ch1 tx 80 rx 0 ev 0 err 0 ovf 0 | ch2 tx 80 rx 0 ev 0 err 0 ovf 0
```

中控发出了请求（`tx 80`），但一个字节都没收到（`rx 0 ev 0`）。三块传感器板都一样。

在这之前，温湿度板曾经成功回应过一次（`03 04 04 01 0A 01 C7 B9 B8`，26.6 ℃、45.5 %），之后换接口、重新烧录传感器后就再也不回了。

### 排查过程

每一步的目的都是把问题范围缩小一半。

| 步骤 | 做法 | 结果 | 结论 |
| --- | --- | --- | --- |
| ① 中控自检 | 拔掉所有传感器，用两根短线把中控 CH1 和 CH2 的 A 接 A、B 接 B，互相收发 | `ch1 tx 160 rx 160 ev 20 err 0 ovf 0 \| ch2 tx 160 rx 160 ev 20 err 0 ovf 0` | **中控两路的发送、接收、收发器、DMA、空闲中断都正常**。问题在线或传感器上 |
| ② 地址对照 | 温湿度板（地址 3）接在 CH1 上，中控在 CH1 上问地址 2 | `rx 0`，没有回应 | 符合 Modbus 规定：地址不是自己的，从机不回应（这一步本身不是故障，但说明了"不回应"不一定是线路问题） |
| ③ 传感器有没有收到 | 中控断电时给传感器复位，再给中控上电，观察传感器板上的 3 个 LED | 中控断电：LED 常亮；中控上电开始发请求：LED 马上熄灭 | 传感器程序**只有收到地址正确的帧**才会按线圈值刷新 LED（线圈默认 0，低电平点亮的 LED 被关掉）。说明**请求到达了传感器，地址也对**。问题缩小到"传感器发送 → 中控"这个方向 |
| ④ 传感器有没有发 | ST-Link 调试传感器板，在课程 `uart_device.c` 的发送函数 `stm32_uart_send` 里打 3 个断点：第 158 行（方向脚 PA8 拉高、准备发送）、第 166 行（发送完成）、第 171 行（发送超时） | 停在**第 171 行**：等"发送完成"信号量超时 | 传感器调用了 `HAL_UART_Transmit_DMA`，但 DMA 发送完成中断（`HAL_UART_TxCpltCallback`）没有执行，回复没有发出去 |
| ⑤ 为什么中断不来 | 看调试器反汇编窗口里当前代码的地址 | `0x0802486C`；工程设置 IROM1 = `0x8020000`，IRAM1 = `0x200000C8` | 烧进去的是 **App 版** |

### 原因

STM32F030 是 Cortex-M0，**没有 VTOR 寄存器**，CPU 只从地址 0 取中断向量。App 版链接在 `0x08020000`，它的中断要能用，必须由 Bootloader 在跳转前完成这一步（课程 `bootloader.c` 的 `RelocateVector()`）：

```c
memcpy((void *)0x20000000, (void *)0x08020000, 200);   /* 把 App 的向量表复制到 RAM 开头 */
__HAL_SYSCFG_REMAPMEMORY_SRAM();                         /* 把地址 0 映射到 RAM */
```

（这也是 App 版的 RAM 从 `0x200000C8` 开始的原因：前 200 字节留给向量表。）

App 版没有经过 Bootloader 直接运行时，地址 0 上不是 App 自己的向量表，中断跳不到 App 的中断处理函数。于是 DMA 发送完成中断进不来 → 信号量一直拿不到 → 发送超时 → 回复没有发出去。

接收方向也依赖中断，但现象表明请求能被处理（LED 会熄灭）。确切的中断走向没有进一步追踪；改烧 Bootloader 版后问题消失，见下一节。

### 解决

把传感器改编成 Bootloader 版重新烧录：

1. Keil：魔术棒 → Target → IROM1 Start 改成 `0x8000000`，Size 改成 `0x20000`（IRAM1 不变，编译器仍用 ARM Compiler 5）
2. Debug → Settings → Flash Download → Erase Full Chip
3. 编译、下载、复位

Bootloader 版自己就在地址 0，向量表天然正确；芯片擦除后没有"固件信息"，它会留在 Bootloader 模式运行完整的传感器程序。

### 验证

开关量板（地址 1）改烧 Bootloader 版后，接在 Hub 的 1 号总线（中控 CH1），中控读输入寄存器（开关量板没有输入寄存器，应回异常 02）：

```
[   2401] D ch1: tx 8 bytes: 01 04 00 00 00 02 71 CB
[   2402] D ch1: rx 5 bytes: 01 84 02 C2 C1
[   2402] W ch1: dev 1: exception 2
[  10109] I probe: ch1 tx 80 rx 45 ev 9 err 0 ovf 0 | ch2 tx 80 rx 0 ev 0 err 0 ovf 0
```

- 回应和预期逐字节一致：地址 01、功能码 04|0x80 = 84、异常码 02、CRC `C2 C1`
- 从发送到收到回应约 1 ms
- 每帧 5 字节、一次接收事件，没有错误

待完成：温湿度板、环境监测板按同样方法重烧并验证。

## 2. 外部修改的源文件被 Keil 覆盖回旧版本

**现象：**`bus_probe.c` 在 Keil 外部更新了（加了超时诊断输出），烧录后串口输出仍是旧版本的格式；检查磁盘上的文件，已经变回旧内容，外部加的代码和在 Keil 里改的一行都不在了。

**原因：**Keil 编辑器里一直打开着这个文件的旧内容。编译前 Keil 会自动保存所有打开的文件，把旧内容写回磁盘，覆盖了外部的修改。

**解决 / 预防：**在 Keil 外修改文件后，Keil 提示"文件已在外部修改，是否重新加载"时选"是"；没有提示的话，先关闭这个文件的标签页再打开。

## 3. `README.md` 被 git 当成二进制文件

**现象：**`git diff --stat` 显示 `README.md | Bin`；文件末尾有一行 `# modbus-gateway`，每个字符后面跟着一个 `0x00` 字节。

**原因：**这一行是按 GitHub 新建仓库页面的提示，在 Windows PowerShell 里用 `echo "# modbus-gateway" >> README.md` 追加的。PowerShell 5 的重定向默认用 UTF-16 编码，和文件其余的 UTF-8 内容混在一起，git 检测到 `0x00` 字节就当成了二进制文件，GitHub 上也会显示乱码。

**解决：**删掉这一行，文件恢复为纯 UTF-8。以后不在 PowerShell 里用 `>` / `>>` 往文本文件里写内容，用编辑器修改。

## 4. PC 测试编译报 `'pdPASS' undeclared`

**现象：**给 `log_init()` 加上 `xTaskCreate(...) != pdPASS` 的检查后，Keil 编译通过，但 PC 上编译 `tests/test_log.c` 报错 `'pdPASS' undeclared`。

**原因：**PC 测试不链接真正的 FreeRTOS，而是用 `tests/stubs/FreeRTOS.h` 这个替身，里面只定义了当时 `log.c` 用到的名字。真正的 FreeRTOS 在 `projdefs.h` 里定义了 `pdPASS`。

**解决：**替身里补上 `#define pdPASS pdTRUE` 和 `#define pdFAIL pdFALSE`（值和真正的 FreeRTOS 一致）。以后被测代码用到新的 FreeRTOS 名字时，替身也要同步补上。

## 5. 一个故障节点影响整条总线

**环境：**Hub 的 1 号总线（中控 CH1）上已经有开关量板（地址 1）和环境监测板（地址 2），两块都稳定回应（约 2 分钟、90 轮：90 / 89 次回应，`err 0`）。温湿度板（地址 3）当时程序还没确认烧对。

**现象：**

- 把温湿度板接到 1 号总线后，从某一轮起，开关量和环境监测**都**不回了：

```
[ 294258] D ch1: tx 8 bytes: 01 04 00 00 00 02 71 CB
[ 294358] W ch1: no byte received in 100 ms
[ 294358] W ch1: dev 1: timeout
```

- 另一次运行中，CH1 的帧错误计数从 30 秒时的 1 涨到 124 秒时的 110，同期只收到 32 次正常回应（80 轮）：

```
[ 124256] I probe: ch1 tx 1920 rx 160 ev 48 err 110 ovf 0 | ch2 tx 1920 rx 0 ev 0 err 2 ovf 0
```

`ev 48` 比正常回应次数（32）多 16 次，多出来的接收事件是乱码触发的。

**分析：**RS485 两线制是所有节点共用一对线，同一时刻只能有一个节点驱动总线。课程传感器程序用 PA8 控制收发芯片的方向：发送前拉高、发完拉低。如果某个节点程序不对（例如没有经过 Bootloader 的 App 版，中断不正常），它可能长时间处于发送状态，或者往线上发不完整的数据：

- 一直占着总线 → 中控的请求和其他节点的回应都被压住，全部超时
- 断续发乱码 → 中控收到格式不对的字节，`err`（帧错误）快速增加，正常回应被打断

拿掉这块板后，同一总线上的其他设备恢复正常。

**结论 / 教训：**

- 新设备先**单独**接到总线上验证，确认能正常回应，再和其他设备一起接
- 统计计数（`err`、`ev` 与正常回应次数的差）能直接反映"总线上有不该有的数据"，比只看超时信息多
- 这也是工业现场把设备分成多条总线、加隔离的原因。中控做成两路独立的 RS485，一路出问题不影响另一路

## 6. 用交换位置分离两个叠加的故障

**现象：**三块板都接在 Hub 上，开关量（地址 1）正常，环境监测（地址 2）和温湿度（地址 3）都不回，看不出原因。

**做法：**把环境监测板和温湿度板**互换位置**，其他不动，重启后观察。

| 板子 | 互换后的位置 | 结果 | 说明 |
| --- | --- | --- | --- |
| 开关量 | 原位（1 号总线） | 正常回应 | 1 号总线、CH1 正常 |
| 温湿度 | 环境监测原来的位置（已证明可用的 1 号总线接口） | 不回 | 问题在**温湿度板自身**（程序），与位置无关 |
| 环境监测 | 温湿度原来的位置 | 两路都不回 | 这块板之前在 1 号总线上工作正常，换到这里就不回 → 问题在**这个接口 / 2 号总线到中控 CH2 这一段** |

**结论：**两个独立的故障叠在一起（温湿度板程序 + 一个不通的接口），所以温湿度板此前从未在 CH2 上出现过。交换位置是把"设备的问题"和"位置的问题"分开的最快方法。

**状态：**暂未修复，不影响第 3 步开发（1 号总线上的两块板可用）。最晚在第 3 步验证两路同时轮询之前处理：温湿度板按 Bootloader 版重烧并单独验证；检查 Hub 2A / 2B 到中控 CH2 的接线和该接口所属的总线。

**10/24 更新：**温湿度板已按 Bootloader 版重烧（Erase Full Chip），接中控 UART4 后 LED 亮后熄灭（收到了发给地址 3 的请求），但中控仍收不到回复。原因未查清，暂时不接。见第 8 条。

## 7. 写单个寄存器的回应被当成回显丢掉

**发现方式：**第 3 步把第 2 步 `bus_probe.c` 里的收发逻辑提成 `mb_master.c`，给它写 PC 测试（`tests/test_mb_master.c`）时，第一次加了"写单个寄存器"的用例，失败：

```
FAIL line 86: mb_master_write_single(&m, 3, MB_TAB_HOLDING, 1, 0x1234, &ex) == MB_OK && s3->regs[1] == 0x1234
mb_master: 23 passed, 1 failed
```

模拟从机的寄存器已经变成了 `0x1234`（从机收到并执行了），但主机返回超时。

**原因：**第 2 步为了兼容"会回显的收发器"，收到的字节如果和请求逐字节一样，就当成回显跳过。读请求没问题（回应第 3 个字节是字节数，和请求不同），但 Modbus 规定功能码 05（写单个线圈）、06（写单个寄存器）的正常回应**就是把请求原样发回来**：

```
请求  03 06 00 01 12 34 + CRC
回应  03 06 00 01 12 34 + CRC     ← 和请求完全一样
```

只收到一份时，程序分不清这是回显还是回应，按回显丢掉，然后等满 100 ms 超时。第 2 步只测了读，所以没暴露。

**解决：**`mb_master_t` 加一个回显模式 `echo`：

| 模式 | 做法 | 用在哪 |
| --- | --- | --- |
| `MB_ECHO_NONE` | 不做回显检查 | 中控板。依据：第 1 条记录里传感器不回应时日志是 `no byte received`，中控连自己发的字节都没收到，说明收发器不回显 |
| `MB_ECHO_ALWAYS` | 每次先跳过一份请求 | 会回显的收发器 |
| `MB_ECHO_AUTO` | 原来的自动判断；05 / 06 只收到一份时，等到超时再当成回应 | 不知道硬件的情况（慢，写一次要等满超时） |

`poll_task.c` 里两个通道都设成 `MB_ECHO_NONE`。加了 3 个用例覆盖三种模式（`test_mb_master.c` 的 14、14b、14c），包括"会回显的收发器 + 从机拔掉时，只收到回显不能算成功"。

**教训：**同一个函数要处理的每一类输入都要有用例。"读"测通了不代表"写"也对；把代码从测试任务提成正式模块时，正好补齐这些用例。

## 8. Hub 1 号总线的数据线不通

**环境：**第 3 步固件（`poll_task`：ch1 轮询开关量 1、环境监测 2；ch2 轮询温湿度 3）。开关量和环境监测插在 Hub 1 号总线上，和 10/20 第 2 步测通时的接法相同，期间没有改动过硬件。

**现象：**两块板都在 2 秒内被判掉线，之后一直不回：

```
[   1600] W ch1: dev 1 switch: offline after 3 failures, retry every 2000 ms
[   1900] W ch1: dev 2 env: offline after 3 failures, retry every 2000 ms
[  10000] I ch1: port tx 200 rx 0 ev 0 err 0 ovf 0 | stack left 478 words
```

中控发出了 25 帧（`tx 200` = 25 × 8 字节），发送都成功了（`send 0`），但串口底层一个字节都没收到（`rx 0`）。

**排查过程：**

| 步骤 | 做法 | 结果 | 结论 |
| --- | --- | --- | --- |
| ① 区分代码和线路 | 看 `port` 行：它是串口最底层的计数，收到任何字节都会加，还没到 Modbus 解析那一层 | `rx 0` | 线上没有任何回应。不是轮询逻辑的问题 |
| ② 传感器收到请求没有 | 中控运行时复位传感器，看 LED（传感器只有收到发给自己的帧才会刷新 LED，见第 1 条③） | 一直亮 | **请求没到传感器** |
| ③ 重新接线 | 断电，把 Hub 到中控的线全部重新接、拧紧 | 不变 | 不是端子松动 |
| ④ 中控自检 | 拔掉 Hub，CH1、CH2 用短线直连，用第 3 步固件 | 10～40 s 之间：ch1 发 232 字节、ch2 收 232；ch2 发 120、ch1 收 120 | **中控两路收发都正常**，问题在中控端子 → Hub → 传感器之间 |
| ⑤ 绕开 Hub | 环境监测板的 A/B 直接接中控 CH1，VIN / GND 仍由 Hub 供电，Hub GND 接中控 GND | `[301] I ch1: dev 2 env: online`；10 秒 `ok 19`、`rx 171`（= 19 × 9 字节）、`err 0` | **传感器和中控都正常，Hub 1 号总线的数据线有问题** |
| ⑥ 开关量也直连 | 开关量板 A/B 也直接接 CH1 | 第一次仍不回；之后两块都 online | 开关量板第一次不回的原因没有确认 |

**④ 里的两个附带发现：**

- **两个主机同时发会撞车。**自检时前 10 秒有丢字节和错误（ch1 `err 4`、ch2 `err 1`、各 `crc 1`）：短接后 CH1、CH2 在同一条总线上，两个任务开机时同时开始发，重试节奏也一样（每 100 ms），帧撞在了一起。判掉线后各自每 2 s 才发一次，就不再撞了。这也是用 Modbus Poll 测传感器时中控必须断开的原因：一条 Modbus 总线上只能有一个主机。
- **中控收发器不回显：**ch1 收到的字节数正好等于 ch2 发的，不包括自己发的。第 7 条把中控设成 `MB_ECHO_NONE` 是对的。

**⑤ 里的另一个现象：**开关量还掉线时，环境监测大约每 2 秒要重试一次（`retry` 每 10 秒 +4～5，`fail 0`），节奏和开关量掉线后的重试一样。推测是总线上刚出现一个没人回答的地址 1 请求后，紧接着发给地址 2 的那一帧有时没被收到。未验证；重试机制保证了数据不丢。

修好以后两块都在线，70 秒里 ch1 的 `retry` 只有开机时的 1 次、之后不再增长（`req 487 ok 487 | timeout 1 retry 1`），**支持这个推测**：环境监测的重试和开关量掉线有关。

10/25 拔插实验又**复现**了一次：拔掉开关量后（39.3 s 判掉线），40～50 s 之间 ch1 `timeout` +10、`retry` +5，而环境监测 `fail 0`、`ok` 照常 19 次——10 次超时里 5 次是开关量每 2 s 的重试，另外 5 次是紧跟其后的环境监测第一次没回、重试成功。插回开关量（54.0 s online）后 `retry` 不再增长。

10/25 第 5 步拔掉开关量时第三次出现（掉线的 10 秒里 ch1 超时比开关量自己的失败多约 6 次，环境监测 `fail 0`）。

具体机理（传感器程序收到别的地址的帧后，为什么会漏掉紧接着的下一帧）没有继续追。对中控的影响：重试兜住了，数据不丢，但每 2 s 多花约 100 ms。

**后续：**排查完以后，把两块传感器的插头在 Hub 1 号总线接口上重新插了一遍，并重新拧紧了 Hub 到中控的端子，**两块都 online 了**。所以 Hub 的 1 号总线并没有断，⑤ 的结论要修正。

**原因：**经过 Hub 的那一段某处**接触不良**，重新插拔后恢复。第 ③ 步只重新接了 Hub 到中控的线，没有好；这次多做了"重新插传感器插头"就好了，所以**传感器插头和 Hub 上的接口**可能性更大。两件事是一起做的，具体是哪一处没有确认。2 号总线之前也不通（第 6 条），可能是同一类问题。

**状态：**开关量、环境监测经 Hub 接中控 CH1，第 3 步继续测试。温湿度板重烧成 Bootloader 版后，接 UART4 时 LED 会熄灭（收到了请求），但中控收不到回复，原因未查（可用课程 `uart_device.c` 发送函数里的断点确认它是否把回复发出去了），暂时不接。

**教训：**

- 线路问题用"绕开一段"来定位：自检排除中控，直连排除 Hub，每一步把范围缩小一半
- "硬件没动过"不等于硬件没变：接口和线材会老化、松动，测通过的接法下次也要重新验证
- 重新插拔就好了的问题最容易再出现。确认的办法：通信时轻轻晃动每一处接头，看 `timeout`、`err` 会不会跳；找到那一处后换线或换接口
- 先看最底层的计数（`port` 行的 `rx`），再看上层的统计，能马上分出是线路问题还是协议问题
